00 About these koans

TypeScript and Svelte

Files this chapter touches

Easel is a shared whiteboard, and the koans build it in two languages: TypeScript and Svelte koans in assets/koans/ run under Vitest, Elixir koans in test/koans/ run under ExUnit. One command runs both:

mix koans

01 TypeScript basics

Files this chapter touches

  • assets/js/guards.ts: isRecord, isFiniteNumber, isString, isColor
  • assets/js/types.ts: PALETTE, Color, Tool (given; read them)

TypeScript is JavaScript plus types that the compiler checks and then erases, so a type never changes what runs. Annotate a binding (const width: number = 1600) or let the compiler infer it: let title = "Easel" is a string, but const title = "Easel" has the literal type "Easel", as it can't change. A type alias names a type: Tool is the union of five literal types "select" | "rect" | "ellipse" | "line" | "pen". An interface names an object's shape; z?: number is an optional field that reads as undefined when missing, and "z" in shape is false then. readonly forbids writes, but only at compile time: Object.freeze(x) is the run-time lock and Object.isFrozen(x) asks for it. Record<Tool, string> holds one string per tool, and (value: unknown) => boolean is a function type. Array entries widen to string like a let, so types.ts writes PALETTE, the 8 strings "#e03131", "#f08c00", ... "#c2255c", with as const: each entry keeps its literal type and the array becomes readonly. (typeof PALETTE)[number] is Color, their union. In a type, typeof X is the type of the value X; in code, typeof is a run-time check.

Data from the server arrives as unknown, which you can't read until a type guard narrows it. A guard returns a boolean, and its return type says what true proves:

function isPoint(value: unknown): value is Point {
  return isRecord(value) && isFiniteNumber(value.x) && isFiniteNumber(value.y)
}

typeof answers with a string such as "number", "string" or "object", and "object" covers null and arrays too; NaN and Infinity are a "number". The koans build shapes with rect() from assets/test/support/fixtures.ts, and rect({ z: 3 }) overrides one field.

02 Modelling shapes

Files this chapter touches

  • assets/js/geometry.ts: bounds, hitTest, moveTo, toBoard, topmostAt, describe
  • assets/js/types.ts: Shape, assertNever (given; read them)

Shape in types.ts is a discriminated union, Rect | Ellipse | Line | Pen: four interfaces that share id, color, x, y and an optional z, and differ in a literal kind field. A rect or an ellipse adds w and h, a line adds dx and dy to its far end, and a pen adds points, each [dx, dy] from x, y. Comparing kind narrows the type, in an if or a switch:

function area(s: Shape): number {
  switch (s.kind) {
    case "rect": return s.w * s.h
    case "ellipse": return (Math.PI * s.w * s.h) / 4
    case "line": case "pen": return 0
    default: return assertNever(s)
  }
}

In the default branch s is never, because every kind has a case, and assertNever(x: never) accepts only that: add a fifth kind and each such switch fails to compile until it handles it. A bad value that gets through at run time throws Error(Unexpected value: ${JSON.stringify(x)}). Types are structural: any object with numeric x and y is a Point, so a shape stands for its start.

Fixtures: rect() is 200 by 100 at 100, 100; ellipse() is 200 by 100 at 400, 300; line() runs from 50, 50 by dx 100, dy 100; pen() starts at 20, 20 with 2 points. The last shape in an array is drawn on top. The board is BOARD_WIDTH by BOARD_HEIGHT (1600 by 1000, in types.ts) at any canvas size. clientX and clientY are measured from the window's top left, like getBoundingClientRect().

03 Components and runes

Files this chapter touches

  • assets/koans/drills/03_counter.svelte: count as state, a button that counts
  • assets/svelte/PeopleList.svelte: count of people, a row per person, just you
  • assets/svelte/ColorPicker.svelte: a radio per colour
  • assets/koans/drills/03_greeting.svelte: name, excited (given; read it)

A .svelte file is a component: a <script lang="ts"> block, then markup. Props arrive through $props(), typed by an interface, and a default fills one left out:

interface Props { name: string; excited?: boolean }
let { name, excited = false }: Props = $props()
<h1>Hello, {name}{excited ? "!" : "."}</h1>

That is the greeting drill: given name "Ada" it shows Hello, Ada. and excited: true ends it in !. let open = $state(false) is state the markup follows: assign to it and the page updates. $derived(expr) is computed from what it reads; a copy made in an $effect lags until the effect runs. Runes work as class fields in .svelte.ts files too. Svelte 4 used export let, $:, on:click, slots and createEventDispatcher; Svelte 5 replaces them with runes, callback props and snippets.

{#if cond}...{:else}...{/if} shows markup on a condition, and {#each items as item (item.id)} repeats it: the key in parentheses, (item.id), moves an item's element when the list is reordered. Svelte drops spaces at the start and end of a block's content, so {#if open} (open){/if} loses its space; keep it in a string: {" (open)"}. An event attribute takes a function, as in <button onclick={() => (open = !open)}>Toggle</button>. A child calls a callback prop such as onpick to tell its parent; reassigning a prop only overrides it locally, and a bound one is declared with $bindable(). Svelte batches DOM updates: right after a click the counter drill, at Clicked 0 times, still shows the old text until flushSync() applies the update.

04 Effects, bindings and the toolbar

Files this chapter touches

  • assets/koans/drills/04_escape_key.svelte: listen for escape
  • assets/koans/drills/04_name_field.svelte: bind the name
  • assets/koans/drills/04_focus_field.svelte: field (given; read it)
  • assets/js/board_state.svelte.ts: upsert, replaceAll, remove, moveShape, ordered, snapshot
  • assets/svelte/Toolbar.svelte: a button per tool, a delete button

$effect(fn) runs fn after the component mounts, then again after any state fn read while it ran changes; only synchronous reads count, not one in a timer or after an await. fn may return a cleanup, run before the next run and on destroy. Below, delay is state: a new delay clears the old timer before the effect starts another, and destroy clears it:

$effect(() => {
  const id = setTimeout(() => (saved = true), delay)
  return () => clearTimeout(id)
})

bind:value={name} ties an input to state both ways: typing sets name, and setting name changes the field. bind:this={field} stores the element once it is mounted, so read it in an effect. let name = $state(initial) reads initial once, and svelte-check warns state_referenced_locally. When a one-time seed is what you mean, say so: $state(untrack(() => initial)).

$state proxies a plain object or array deeply, so a push inside it is seen. A Map, Set or class instance is not proxied, so its .set is never seen (svelte/reactivity has SvelteMap). $state.raw never proxies: only assigning a new value is seen. BoardState keeps its shapes in a raw ReadonlyMap; in a method, this is the instance, so this.shapes = next assigns a new one. $state.snapshot(x) is a plain copy of a proxy. In a koan, $effect.root(fn) hosts effects.

05 Drawing on a canvas

Files this chapter touches

  • assets/js/render.ts: fitCanvas, drawShape, drawBoard
  • assets/js/tools.ts: pointerDown, pointerMove, stretch, pointerUp
  • assets/svelte/Canvas.svelte: the canvas element, the redraw effect, down, move, up
  • assets/test/support/fake_context.ts: createFakeContext (given; read it)

A canvas is pixels painted through its 2D context, canvas.getContext("2d"). ctx.strokeStyle = color picks the ink, beginPath() starts a path, moveTo(x, y) lifts the pen to a point, lineTo(x, y) adds a line to the next point and stroke() inks the path. strokeRect(x, y, w, h) outlines a box in one call, clearRect(x, y, w, h) wipes one, and an X is one path of two lines:

ctx.beginPath()
ctx.moveTo(0, 0)
ctx.lineTo(8, 8)
ctx.moveTo(8, 0)
ctx.lineTo(0, 8)
ctx.stroke()

canvas.width sizes the bitmap and CSS sizes the box; it is sharp with devicePixelRatio bitmap pixels per CSS pixel (500 CSS pixels at dpr 3 want 1500). Easel's bitmap is the 1600 by 1000 board times dpr, scaled by CSS to fit. setTransform(a, b, c, d, e, f) maps later calls: a and d scale x and y, b and c skew, e and f shift. Setting canvas.width resets the context, so size first.

tools.ts is a state machine: pointerDown, pointerMove and pointerUp take a ToolState and return a new one. idle becomes drawing (an origin and a growing draft) or dragging (a shape id and the grab offset); pointerUp goes back to idle with a commit, an add or a move, or null. On down, setPointerCapture(event.pointerId) sends its events here until pointerup or pointercancel.

Files this chapter touches

  • lib/easel_web/live/board_live.ex: EaselWeb.BoardLive.render/1, svelte_props/1

A LiveView hands a Svelte component its props. live_svelte's <.svelte> function component renders one div: data-name names the component, data-props holds the props as JSON, and phx-hook="SvelteHook" names the browser hook that mounts it. Props go through JSON, so atom keys arrive as strings; the browser adds live, the hook itself, to the props it hands down.

<.svelte name="Clock" props={%{zone: @zone, ticks: 0}} socket={@socket} />

A page renders twice. The static render answers a plain GET with HTML: mount runs with connected?(socket) false, so BoardLive skips join/2 and renders the assigns mount gave it, no shapes, sync_id 0 and nobody here. Then the browser connects and mount runs again, connected; chapters 08 to 13 fill that path. In a koan, get(conn, path) is the static render and get_svelte(html) reads the div back as a map with :name, :id, :props and :ssr among others. The hook mounts only after the connected render is patched in, so with SSR off the browser never uses the static render's props; koans read them because they need no socket. socket={@socket} tells live_svelte the render is connected, so later renders send only the props that changed (data-props-diff); without it every render resends them all. Passing assigns to svelte_props/1 turns off change tracking for that call; live_svelte diffs itself.

live_svelte can also render the component on the server (SSR), in Node. Easel turns that off with config :live_svelte, ssr: false: a canvas has no server HTML worth sending, and Node stays a build tool. So the div's inner target holds no component markup, its text only whitespace, "" once trimmed, and :ssr is false, until the hook mounts the component.

07 Boards and shapes in SQLite

Files this chapter touches

A throttle runs the first call at once, the leading edge, and holds later calls for a window of ms milliseconds, keeping only the latest, which runs when the window ends, the trailing edge, so the last position is never lost. After the window the next call leads again. A debounce waits for the calls to stop instead, so a pointer moving steadily would never be sent. This limiter keeps the leading edge only, and a cursor drawn with it stops short:

function oncePer(fn: () => void, ms: number): () => void {
  let last = -Infinity
  return () => { if (Date.now() - last >= ms) { last = Date.now(); fn() } }
}

throttle.ts keeps lastRun, held (the latest arguments) and timer; the given run(args) cancels what waits, stamps lastRun with now(), Date.now by default, and calls fn. makeCursorSender(live, ms = 50) pushes cursor:move through a throttle, x and y rounded, as the server takes integers only: one per 50 ms. Board calls its cancel() when it unmounts. The throttle is the client being polite; the server checks only for integers, and a rate limit there would drop the rest.

13 Every browser converges

TypeScript and Svelte

Files this chapter touches

  • assets/js/resync.ts: applyProps
  • lib/easel_web/live/board_live.ex (this chapter's Elixir koans)
  • lib/easel/boards/board_server.ex (this chapter's Elixir koans)

From the Phoenix course (chapter 10, LiveView basics, and chapter 13 on reconnects): a dropped socket reconnects by itself and the server mounts again, in a new process. The page stays, and so does live_svelte's hook element, so LiveView calls the hook's updated() with the new props, never mounted(): Board and its BoardState survive the reconnect. LiveView also calls a hook's disconnected() and reconnected() around a rejoin; a rejoin that fails reloads the page, and everything mounts fresh.

So each connected mount sends a fresh sync_id with its snapshot, and Board's effect hands both to applyProps(state, props). A sync_id other than the state's means "this is the whole board now": replace every shape and keep the new id. The same sync_id changes nothing. Other, not greater: sync ids are unique integers for this run of the app, not a count: after a restart they start low again, so compare with !==. A playlist that reloads on a new version does the same:

if (next.version !== list.version) list.load(next.tracks, next.version)

Between resyncs the browser runs ahead. A drawn shape shows at once and goes out as shape:add; its echo, shape:added with the z the server gave it, replaces it by id. Moves carry whole positions, so the server's order decides: the last move it applies wins, in every browser, the sender's too: one process, the board server, sends every op, and messages from one process arrive in the order sent. A move it applied earlier is lost, with no merge and no warning; a delete beats any move, and since nothing remembers a deleted id, a late add with that id brings it back.

Every viewer comes back to the board server's state. A LiveView lives as long as its socket: when the connection drops the process ends, and the reconnect mounts a new one. That runs join/2 again in its given order (tab id, ensure_started, subscribe, track_presence, snapshot, sync_id), so the new process has a new tab, the board as the server holds it now, and a fresh sync_id, on which the browser's surviving component resyncs (the TypeScript koans).

The board server can restart under its viewers instead: it crashes, and the DynamicSupervisor starts it again from the database, or it stopped when idle, and the next call started it again (chapter 08's call/2); every start announces. A crash still saves in terminate/2; a :kill skips it and loses the ops in the save window. init/1 calls announce_restart/1, which broadcasts :board_restarted on the board's topic, and each BoardLive answers it as a reconnect would: a fresh snapshot and a new sync_id. live_svelte then sends only the props that changed, which it can tell only with socket={@socket}. A shop's price list does the same when its prices reload:

def handle_info(:prices_reloaded, socket),
  do: {:noreply, assign(socket, prices: Prices.all(), version: Prices.version())}

One race is left. ensure_started/1 looks a board up before it asks the supervisor, so only a caller that has just seen the board die can race the DynamicSupervisor's restart of it; closing that too would take restart: :temporary and call/2's retry alone.
